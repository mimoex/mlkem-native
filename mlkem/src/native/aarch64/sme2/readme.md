このアセンブリは、今回のML-KEM-768/SME2実装の中心部分です。

大きく分けると、次の5つの処理があります。

1. `S5234_ENTER`：述語レジスタの初期化
2. `S5234_PAIR_GEMM`：SMOPAによる16要求の積和
3. `S5234_STORE_TILE`：ZAからZレジスタを経由してRAMへ保存
4. `S5234_FUNC`：16要求・8ブロック・4出力のループ制御
5. `sme2_pack_secret_d3_body`：要求側係数のZAによる転置

特に重要なのは、`S5234_PAIR_GEMM` が積和演算を担当し、`S5234_FUNC` がそれを何回・どの順序で実行するかを決めているという関係です。

## 2. 条件付きコンパイルとアセンブリの配置

```
#include "../../../common.h"

#if defined(MLK_ARITH_BACKEND_AARCH64) && \
```

この部分はCPU上で実行されるアセンブリ命令ではなく、Cプリプロセッサによるビルド条件です。

AArch64の算術バックエンドとSME2が有効で、共有実装に関する条件を満たすときだけ、後続のコードがアセンブル対象になります。

最後の条件は「ML-KEM-768（`MLKEM_K == 3`）または共有構成」です。共有構成なら、別のパラメータセットのビルドにも関数定義が含まれる可能性があります。ただし、カーネル内部の入力数は3に固定されています。

```
.text
.p2align 2
```

- `.text`：以下を機械語のコード領域に配置する。
- `.p2align 2`：アドレスを \\(2^2=4\\) バイト境界に整列する。

また、

```
.macro S5234_PAIR_GEMM
    ...
.endm
```

はアセンブラのマクロ定義です。C言語の関数とは異なり、呼び出し位置に命令列が展開されます。

`MLK_ASM_NAMESPACE(...)` は、ライブラリの名前空間に対応したシンボル名を生成するためのマクロです。

## 3. `S5234_ENTER`：述語レジスタの初期化

```
.macro S5234_ENTER
    ptrue p0.h
    ptrue pn8.h
    ptrue pn9.s
.endm
```

### `ptrue p0.h`

`PTRUE` は、述語レジスタの対象レーンを有効にする命令です。

- `p0`：通常の述語レジスタ
- `.h`：16-bit（halfword）単位

SVL=512-bitの場合、16-bit要素が32個あるため、`p0.h` は32レーンすべてを有効にします。

この述語は後で、

```
ld1h {z4.h}, p0/z, [x4]
```

および、

```
smopa za0.s, p0/m, p0/m, z0.h, z4.h
```

に使用します。

`/z` は無効レーンをゼロにする形式、`/m` は無効部分を演算対象から除外するマージ形式です。

今回の処理では全レーンが有効なので、端数処理はありません。

### `ptrue pn8.h` と `ptrue pn9.s`

`pn8` と `pn9` は、SME2で追加された predicate-as-counter 形式で使用する述語レジスタです。複数のZレジスタを一括操作する際、複数ベクトルにまたがる有効要素を指定できます。独立した整数カウンタレジスタではありません。

## 4. `S5234_PAIR_GEMM`：積和計算の中心

このマクロが最も重要です。

### 4.1 ZAタイルをゼロ初期化する

```
zero {za0.s, za1.s}
zero {za2.s, za3.s}
```

4個の32-bit ZAタイルをゼロクリアします。

Apple M4では各タイルが16×16の32-bit要素を保持します。

\\[ 16\times16\times4=1024\text{ B} \\]

4タイル合計で4,096 Bです。

これから48反復分の積和結果を蓄積するため、最初にすべて0へ初期化します。

この初期化は48反復の前に1回だけ行います。 反復の途中では初期化しません。

### 4.2 ループカウンタを48に設定する

```
mov x27, #48
```

`MOV` は値をレジスタに設定する命令です。

ここでは `x27 = 48` とします。

48の意味は、

\\[ 3\text{入力多項式}\times \frac{32\text{係数}}{2\text{係数/反復}} =48 \\]

です。

### 4.3 要求側の係数をz4へロードする

```
ld1h {z4.h}, p0/z, [x4]
```

`LD1H` は、メモリから16-bit要素を読み込む命令です。

| 記法     | 意味                     |
| ------ | ---------------------- |
| `ld1h` | 16-bit単位のロード           |
| `z4.h` | Z4を16-bit要素の集合として扱う    |
| `p0/z` | p0で指定したレーンを読み、無効レーンはゼロ |
| `[x4]` | x4が指すメモリアドレスから読み込む     |

ここでは、すでに転置された要求側データを読み込みます。

最初の反復であれば、

\\[ z4= [y\_{0,0},y\_{0,1}, y\_{1,0},y\_{1,1}, \ldots,y\_{15,0},y\_{15,1}] \\]

という配置です。

\\[ 16\text{要求}\times2\text{係数}\times2\text{ B} =\boxed{64\text{ B}} \\]

したがって、1命令で512-bitのZ4を満たします。

### 4.4 公開側の係数をz0〜z3へロードする

```
ld1h {z0.h-z3.h}, pn8/z, [x8]
```

これはSME2の複数ベクトルロード命令です。

1回でZ0、Z1、Z2、Z3の4本を読み込みます。

\\[ 4\times64=256\text{ B} \\]

各Zレジスタには、Toeplitz行列の16行から取り出した2列分の係数が格納されます。

最初の反復であれば、概念的には次の配置です。

| レジスタ | 読み込むデータ                    |
| ---- | -------------------------- |
| `z0` | 出力AのToeplitz行列、行0〜15・列0,1  |
| `z1` | 出力AのToeplitz行列、行16〜31・列0,1 |
| `z2` | 出力BのToeplitz行列、行0〜15・列0,1  |
| `z3` | 出力BのToeplitz行列、行16〜31・列0,1 |

ここで「行0〜15」とは16行×2係数の32個の値であって、単純に公開多項式の係数0〜15をそのまま並べる意味ではありません。

### 4.5 SMOPAを4回実行する

```
smopa za0.s, p0/m, p0/m, z0.h, z4.h
smopa za1.s, p0/m, p0/m, z1.h, z4.h
smopa za2.s, p0/m, p0/m, z2.h, z4.h
smopa za3.s, p0/m, p0/m, z3.h, z4.h
```

例えば1行目を分解すると、

| オペランド       | 意味               |
| ----------- | ---------------- |
| `smopa`     | 符号付き整数の外積和を累積    |
| `za0.s`     | 累積先の32-bit ZAタイル |
| `p0/m`（1つ目） | 公開側の有効レーン        |
| `p0/m`（2つ目） | 要求側の有効レーン        |
| `z0.h`      | 公開側の16-bit係数     |
| `z4.h`      | 要求側の16-bit係数     |

です。

16-bit×16-bitの2-way SMOPAは、ZAの各32-bit要素に2つの積を加算します。

[image](https://www.google.com/s2/favicons?domain=https://developer.arm.com\&sz=32)

developer.arm.com



\\[ ZA0[i,r]\mathrel{+}= T_A[i,2t]y\_{r,2t} + T_A[i,2t+1]y\_{r,2t+1} \\]

ここで \\(i\\) は出力係数位置、\\(r\\) は要求番号、\\(t\\) は処理中の係数ペア番号です。

1回のSMOPAで、

\\[ 16\times16\times2=512 \\]

個の16-bit係数積を計算して、256個の32-bit累積要素を更新します。

4命令では、

\\[ 4\times512=2048 \\]

個の係数積に相当します。

なお、「並列」とは4つの独立したタイルへ積和を行うという意味です。CPU内部で4命令が厳密に同じクロックに実行されるという意味ではありません。

### 4.6 ポインタを次の係数ペアへ進める

```
add x4, x4, #64
add x8, x8, #256
```

`ADD` は加算です。

今回は、次のメモリアドレスへ進めるために使用しています。

- `x4 += 64`：次の要求側係数ペアへ進む。
- `x8 += 256`：次の公開側4ベクトルへ進む。

最初の反復では係数0,1を処理し、次の反復では係数2,3を処理します。

### 4.7 ループカウンタを減らして分岐する

```
subs x27, x27, #1
b.ne .Ls5234_kp_\@
```

`SUBS` は減算すると同時に、条件フラグを更新します。

`B.NE` は「直前の比較・演算結果がゼロでなければ分岐」です。

したがって、

```
x27--;

if (x27 != 0) {
    goto loop_start;
}
```

と同じ意味です。

48回実行すると、`x27=0` になってループを抜けます。

`\@` はアセンブラのマクロ展開ごとに異なる番号を生成する仕組みで、マクロを複数回展開してもローカルラベルが衝突しないようにしています。

### 4.8 48反復をC言語風に書くと

```
ZA0 = ZA1 = ZA2 = ZA3 = 0;

for (int k = 0; k < 3; k++) {
    for (int t = 0; t < 16; t++) {

        z4 = load_secret(k, t);

        z0 = load_public(outputA, 0, k, t);
        z1 = load_public(outputA, 1, k, t);
        z2 = load_public(outputB, 0, k, t);
        z3 = load_public(outputB, 1, k, t);

        SMOPA(ZA0, z0, z4);
        SMOPA(ZA1, z1, z4);
        SMOPA(ZA2, z2, z4);
        SMOPA(ZA3, z3, z4);
    }
}
```

実際のアセンブリでは `k` と `t` を個別に管理せず、48回のフラットなループとして実装しています。

公開側・要求側データは、すでに `k=0` の係数ペア0〜15、`k=1` の係数ペア0〜15、`k=2` の係数ペア0〜15の順序でメモリに配置されている必要があります。

## 5. `S5234_STORE_TILE`：ZAから結果を取り出す

このマクロは、SMOPAで累積したZAの32-bit結果を、Zレジスタへ移してRAMに書き出す処理です。

### 5.1 行番号を0にする

```
mov w12, #0
```

`w12` は、ZAから読み出す行の位置を指定するために使用します。

### 5.2 ZAの4行をZレジスタへ移動する

```
mova {z28.s-z31.s}, \ZA\().s[w12, 0:3]
```

この命令が、以前話題にした ZA→Zレジスタの直接転送です。

`MOVA` はZAのスライスとZレジスタ間でデータを転送する命令です。ここではSME2の4スライス形式を使用しています。

[image](https://www.google.com/s2/favicons?domain=https://developer.arm.com\&sz=32)

developer.arm.com

+1



例えば、呼び出しが

```
S5234_STORE_TILE za0h, x2
```

なら、

```
mova {z28.s-z31.s}, za0h.s[w12, 0:3]
```

に展開されます。

`w12=0` の場合、

| 転送元         | 転送先 |
| ----------- | --- |
| ZA0の水平スライス0 | Z28 |
| ZA0の水平スライス1 | Z29 |
| ZA0の水平スライス2 | Z30 |
| ZA0の水平スライス3 | Z31 |

となります。

各水平スライスは、16個の32-bit整数を含むので64 Bです。

4行をまとめて転送すると、

\\[ 4\times64=256\text{ B} \\]

です。

### 5.3 RAMへ32-bit値を書き出す

```
st1w {z28.s-z31.s}, pn9, [\PTR]
```

`ST1W` は32-bit（word）単位のストア命令です。

4本のZレジスタから合計256 Bを書き出します。

ここでは剰余還元せず、ZAの32-bit累積結果をそのままメモリに書き出しています。

### 5.4 次の4行へ進む

```
add \PTR, \PTR, #256
add w12, w12, #4

cmp w12, #16
b.lt .Ls5234_store_\@
```

- 出力先ポインタを256 B進める。
- ZAの読み出し位置を4行進める。
- `CMP` で16と比較する。
- `B.LT` で16未満なら繰り返す。

| 反復 | ZAから取り出す行 | RAMへの保存量 |
| -- | --------- | -------- |
| 1  | 0〜3       | 256 B    |
| 2  | 4〜7       | 256 B    |
| 3  | 8〜11      | 256 B    |
| 4  | 12〜15     | 256 B    |
| 合計 | 16行すべて    | 1,024 B  |

これでZAタイル1個の内容をすべてRAMに書き出せます。

また、このコードでは水平スライスで取り出すので、現在のSMOPA配置を前提とすると、1行はある出力係数位置についての16要求分の結果です。

この点は重要です。後続の逆NTTが要求ごとの係数配列を必要とするなら、ここで書き出したデータをさらに再配置する必要があります。

## 6. `S5234_FUNC`：全体のループを制御する

ここまでの2つのマクロは、主に「積和する」「保存する」という演算を担当していました。

`S5234_FUNC` は、それらを組み合わせて、16要求・8ブロック・4出力を処理する関数を生成します。

### 6.1 引数と関数名

```
.macro S5234_FUNC NAME, STORE

.p2align 2
.globl \NAME
\NAME:
```

- `NAME`：生成する関数のシンボル名
- `STORE`：ZAの結果をRAMに書き出すかどうか
- `.globl`：そのシンボルを他のコードから参照可能にする
- `\NAME:`：関数の開始位置

最後の、

```
S5234_FUNC MLK_ASM_NAMESPACE(sme2_cross_matrix_d3_body), 1
```

によって、実際の関数が生成されます。

`STORE=1` なので、ZAの結果は `raw_out` に保存されます。

### 6.2 group数が0なら終了

```
cbz x3, .Ls5234_done_\@
```

`CBZ` は Compare and Branch on Zero です。

`x3 == 0` なら終了ラベルへ分岐します。

今回、`x3` には処理する16要求groupの数が入っています。

### 6.3 汎用レジスタをスタックに退避する

```
sub sp, sp, #0x90

stp x19, x20, [sp, #0]
stp x21, x22, [sp, #16]
stp x23, x24, [sp, #32]
stp x25, x26, [sp, #48]
stp x27, x28, [sp, #64]
```

`SUB` によってスタックポインタ `sp` を144 B下げ、領域を確保しています。

`STP` は2本のレジスタをまとめてメモリに保存する命令です。

AArch64の通常の呼び出し規約では、`x19`〜`x28` はcallee-savedレジスタです。関数が変更した場合、呼び出し元に戻る前に元の値を復元する必要があります。

このコードでは10本、合計80 Bを保存しています。確保した144 Bのうち残り64 Bは、提示されたコードでは使用されていません。

### 6.4 引数をループ用レジスタに保存する

```
S5234_ENTER

mov x19, x0
mov x20, x1
mov x21, x2
mov x22, x3
```

ここで述語を初期化し、引数を保存します。

| レジスタ  | 内容                |
| ----- | ----------------- |
| `x19` | 公開側の先頭。全groupで再利用 |
| `x20` | 現在の要求groupの先頭     |
| `x21` | 現在のraw出力groupの先頭  |
| `x22` | 残りgroup数          |

`x19`をgroupごとに進めないことが、同一公開鍵を再利用する仕組みです。

### 6.5 groupループ

```
.Ls5234_group_\@:
    mov x23, x19
    mov x24, x20
    mov x25, x21

    mov x26, #8
```

現在のgroupについて、ブロック処理用ポインタを初期化します。

- `x23`：公開側の現在ブロック
- `x24`：要求側の現在ブロック
- `x25`：出力先の現在ブロック
- `x26`：残り8ブロック

3段NTTにより8個の32係数ブロックに分解されているので、ここで8回のループを設定します。

### 6.6 前半2出力を計算する

```
.Ls5234_block_\@:
    mov x4, x24
    mov x8, x23
    S5234_PAIR_GEMM
```

`x4` を要求側の現在ブロック先頭、`x8` を公開側の現在ブロック先頭に設定します。

その後、先ほど説明した48反復のSMOPAを実行します。

このとき計算するのは `dot0, dot1` の2出力分です。これらが \\(u_0,u_1\\) に対応するかどうかは、公開側の事前計算データの格納順で確定します。

```
.if \STORE
    mov x2, x25
    S5234_STORE_TILE za0h, x2
    S5234_STORE_TILE za1h, x2
    S5234_STORE_TILE za2h, x2
    S5234_STORE_TILE za3h, x2
.endif
```

4個のZAを順番に書き出します。

\\[ 4\times1024=\boxed{4096\text{ B}} \\]

です。

### 6.7 後半2出力を計算する

```
mov x4, x24
mov x11, #24
add x8, x23, x11, lsl #12
S5234_PAIR_GEMM
```

ここが特に重要です。

`mov x4, x24` によって、要求側ポインタを同じブロックの先頭へ戻しています。

なぜなら、後半2出力でも同じ16要求の \\(y_0,y_1,y_2\\) を使うからです。

一方、公開側は、

```
mov x11, #24
add x8, x23, x11, lsl #12
```

で別の領域に移動します。

`LSL #12` は12ビット左シフト、つまり4096倍です。

\\[ 24\times4096=98304\text{ B} \\]

これは前半2出力の公開側データ8ブロック分に相当します。

\\[ 8\times12288=98304\text{ B} \\]

したがって、公開側の後半2出力用領域を読み込みます。

後半の保存処理は、

```
add x2, x25, #1, lsl #12
```

で出力先を4096 B進めてから、4個のZAを書き出します。

これで1ブロックに対して4出力分、合計8192 Bが完成します。

### 6.8 次のブロックへ進む

```
add x23, x23, #3, lsl #12
add x24, x24, #3072
add x25, x25, #2, lsl #12

subs x26, x26, #1
b.ne .Ls5234_block_\@
```

各ポインタの移動量は次のとおりです。

| ポインタ      | 移動量      | 計算根拠            |
| --------- | -------- | --------------- |
| 公開側 `x23` | 12,288 B | 48反復×4本×64 B    |
| 要求側 `x24` | 3,072 B  | 48反復×64 B       |
| 出力側 `x25` | 8,192 B  | 2ペア×4 ZA×1024 B |

`x26` を減らし、0になるまで8ブロックを処理します。

### 6.9 次の16要求groupへ進む

```
mov x11, #6
add x20, x20, x11, lsl #12

mov x11, #16
add x21, x21, x11, lsl #12

subs x22, x22, #1
b.ne .Ls5234_group_\@
```

8ブロックが完了すると、次の16要求groupへ移動します。

要求側は、

\\[ 8\times3072=24576\text{ B} \\]

出力側は、

\\[ 8\times8192=65536\text{ B} \\]

進みます。

一方、公開側の基準ポインタ `x19` は変更されません。

したがって、次の16要求groupでも、同一公開鍵の事前計算済みToeplitz係数を再利用する構造です。

最後に `LDP` で退避した汎用レジスタを復元し、`SP` を戻して `RET` で終了します。

## 7. `sme2_pack_secret_d3_body`：ZAによる入力転置

これも今回の実装の重要な最適化です。

SMOPAに入力する要求側データを、要求ごとの配置から係数ペアごとの配置へ変更します。

### 7.1 入力・出力のレイアウト

入力は通常の要求単位配置です。

```
要求0: y0,0 y0,1 y0,2 y0,3 ... y0,31
要求1: y1,0 y1,1 y1,2 y1,3 ... y1,31
...
要求15: ...
```

出力は、

```
pair0: y0,0 y0,1 y1,0 y1,1 ... y15,0 y15,1
pair1: y0,2 y0,3 y1,2 y1,3 ... y15,2 y15,3
...
pair15: ... y15,30 y15,31
```

という配置です。

### 7.2 述語とループの初期化

```
ptrue p0.s

mov x4, x0
mov x5, x1
mov x6, #8
```

ここでは、16個の32-bit要素すべてを有効にするために `p0.s` を設定します。

32-bit要素として読み書きする理由は、隣接する2個の16-bit係数を1個の32-bit値としてまとめて扱うためです。

この段階では数値演算は行わず、ビット列をそのまま移動します。

`x4` は入力側のブロック先頭、`x5` は出力側のブロック先頭、`x6` は8ブロックのカウンタです。

### 7.3 3入力多項式を処理する

```
.Lsme2_pack_block:
    mov x7, x4
    mov x8, x5
    mov x9, #3
```

`x9=3` はML-KEM-768の3入力多項式に対応します。

### 7.4 ZAの水平方向へ16要求をロード

```
mov x10, x7
mov w12, #0

.Lsme2_pack_row:
    ld1w {za0h.s[w12, 0]}, p0/z, [x10]
    add x10, x10, #1536
    add w12, w12, #1
    cmp w12, #16
    b.lo .Lsme2_pack_row
```

`LD1W` により、1要求の32係数を16個の32-bitペアとして、ZAの1行へロードします。

`1536 B` は、

\\[ 3\text{多項式}\times256\text{係数}\times2\text{ B} =1536\text{ B} \\]

であり、隣の要求に進むためのストライドです。

16要求分をロードすると、ZA0は概念的に次の状態になります。

ZA0：転置前の16×16行列

各行が1要求、各列が係数ペアを表します。青い列は16要求の係数ペア(0,1)です。

### 7.5 垂直方向から読み出して保存する

```
mov x10, x8
mov w12, #0

.Lsme2_pack_col:
    st1w {za0v.s[w12, 0]}, p0, [x10]
    add x10, x10, #64
    add w12, w12, #1
    cmp w12, #16
    b.lo .Lsme2_pack_col
```

ここでは `ZA0V`、すなわち垂直方向のスライスを使用します。

水平ロードでZAの各行に要求ごとの係数を配置し、垂直ストアで同じ係数ペアに属する16要求分をまとめて取り出します。

具体的には、1列が、

\\[ [y\_{0,2t},y\_{0,2t+1}, y\_{1,2t},y\_{1,2t+1},\ldots, y\_{15,2t},y\_{15,2t+1}] \\]

になります。

これは、先ほどの `S5234_PAIR_GEMM` が `z4` にロードする64 Bと同じ形式です。

この水平ロード・垂直ストアが、今回のZAを用いた要求側データ転置です。

### 7.6 次の多項式・ブロックへ進む

```
add x7, x7, #512
add x8, x8, #1024

subs x9, x9, #1
b.ne .Lsme2_pack_poly
```

512 Bは元の1多項式のサイズです。

\\[ 256\times2=512\text{ B} \\]

1024 Bは転置後の1ブロック・1入力多項式・16要求分のサイズです。

\\[ 16\text{係数ペア}\times64\text{ B}=1024\text{ B} \\]

さらに、

```
add x4, x4, #64
add x5, x5, #3072

subs x6, x6, #1
b.ne .Lsme2_pack_block
```

で次の32係数ブロックへ進みます。

入力側は32係数×2 Bで64 B、出力側は3入力×1024 Bで3072 B進みます。

したがって、16要求group全体では、

\\[ 8\times3072=\boxed{24576\text{ B}} \\]

の転置済み要求側データが生成されます。

ここで注意すべきなのは、この転置関数自身は16要求groupを1個だけ処理するということです。複数groupの反復は呼び出し側が担当する必要があります。

## 8. データ構造とポインタの対応を整理する

ここまでのアドレス計算から、メモリ配置を次のように表現できます。

実際のC構造体定義ではなく、アセンブリのアクセスを説明するための論理配列です。

```
// 同一鍵の事前計算済み公開側データ
int16_t public_gemm[2][8][3][16][4][32];

// 16要求groupごとの転置済み要求側データ
int16_t secret_gemm[G][8][3][16][16][2];

// 各groupの32-bit積和結果
int32_t raw_out[G][8][2][4][16][16];
```

ここで `G` はgroup数です。

| 配列の次元                 | 意味               |
| --------------------- | ---------------- |
| `public_gemm` の `[2]` | 2出力ずつのペア         |
| `[8]`                 | 3段NTTの8ブロック      |
| `[3]`                 | 3入力多項式           |
| `[16]`                | 16個の係数ペア         |
| `[4]`                 | 4つのZAに対応する公開側Z   |
| `[32]`                | 1本のZに入る16-bit係数数 |

そして、各groupの必要メモリ量は、

| データ                  | サイズ       |
| -------------------- | --------- |
| 公開側事前計算データ（全group共通） | 196,608 B |
| 要求側転置データ（1 group）    | 24,576 B  |
| raw出力（1 group）       | 65,536 B  |

この配置によって、内側ループでは添字計算を繰り返さず、単純なポインタ加算だけで次のデータを読み出せています。

## 9. 全体をC言語の擬似コードにすると

最終的に、このアセンブリの演算経路は次のように整理できます。

```
void sme2_cross_matrix_d3(
    const int16_t *public_gemm,
    const int16_t *secret_gemm,
    int32_t *raw_out,
    size_t groups)
{
    init_predicates();

    for (size_t g = 0; g < groups; g++) {

        for (int b = 0; b < 8; b++) {

            // 4出力を2出力ずつ処理
            for (int pair = 0; pair < 2; pair++) {

                zero(ZA0, ZA1, ZA2, ZA3);

                // 3入力 × 16係数ペア
                for (int k = 0; k < 3; k++) {
                    for (int t = 0; t < 16; t++) {

                        z4 = load_secret(g, b, k, t);

                        z0 = load_public(pair, b, k, t, 0);
                        z1 = load_public(pair, b, k, t, 1);
                        z2 = load_public(pair, b, k, t, 2);
                        z3 = load_public(pair, b, k, t, 3);

                        smopa(ZA0, z0, z4);
                        smopa(ZA1, z1, z4);
                        smopa(ZA2, z2, z4);
                        smopa(ZA3, z3, z4);
                    }
                }

                store_tile(ZA0, raw_out);
                store_tile(ZA1, raw_out);
                store_tile(ZA2, raw_out);
                store_tile(ZA3, raw_out);
            }
        }
    }
}
```

これは理解用の擬似コードなので、実際の配列添字やアドレス更新は省略しています。

演算回数も確認できます。

| 単位            | SMOPA数 |
| ------------- | ------ |
| 1反復           | 4      |
| 1出力ペア・1ブロック   | 192    |
| 2出力ペア・1ブロック   | 384    |
| 8ブロック・1 group | 3,072  |

32-bit結果のメモリ書き出しは、

\\[ 8\text{ブロック}\times2\text{ペア} \times4\text{タイル}\times1024\text{ B} =65536\text{ B/group} \\]

です。

## 10. このコードを読むうえでの注意点

最後に、提示されたコードから確定できることと、別ファイルを見る必要があることを区別します。

| 項目                                      | 状態             |
| --------------------------------------- | -------------- |
| 16要求の係数ペアをZ4へロード                        | 確認できる          |
| 4本の公開側Zで4つのZAへSMOPA                     | 確認できる          |
| 48反復による3入力積和                            | 確認できる          |
| 4出力を2ペアに分割                              | 確認できる          |
| 公開側係数をgroup間で再利用                        | 確認できる          |
| ZAの結果をZ経由でRAMへ保存                        | 確認できる          |
| ZAを使った要求側転置                             | 確認できる          |
| 公開側のToeplitz係数・\\(\gamma_b\\) の生成方法     | 別ファイルの確認が必要    |
| `dot0`〜`dot3`と\\(u_0,u_1,u_2,v\\)の厳密な対応 | 公開側パック処理の確認が必要 |
| 剰余還元と3段逆NTT                             | このコードには含まれない   |
| `SMSTART`・`SMSTOP`による実行状態管理             | このコードには含まれない   |

なお、このコード内には剰余還元命令がありません。ZAでは32-bit整数として96係数積を累積するため、オーバーフローしないという保証は、別途、実際の入力係数の範囲に基づいて示す必要があります。

また、`sme2_pack_secret_d3_body` と `sme2_cross_matrix_d3_body` のどちらにも `SMSTART`・`SMSTOP` はありません。コメントどおり、StreamingモードとZAの有効化は呼び出し側で管理する設計です。

次にソースコードを確認するなら、`public_gemm` を生成しているToeplitz展開処理が最も重要です。 そこを読めば、公開多項式の32係数と \\(\gamma_b\\) から、`z0`〜`z3`にロードされる32個の値がどの順番で作られるかまで、完全につながります。
